# Information architecture: PDF.co merge documentation

This document explains how the PDF.co merge sample is organized, why it uses this structure, and how it would scale.

## Repository layout

```
assignment/
├── README.md                          # Assignment index, topic selection, component map
├── process/                           # Author-facing workflow (any API topic)
│   ├── information-architecture.md    # this document
│   ├── lifecycle.md
│   ├── dynamic-updates.md
│   ├── ai-assisted-docs-workflow.md
│   └── ai/
│       ├── skills/                    # Agent Skills (SKILL.md per directory)
│       └── rules/
│           └── pdfco-style-guide.md
└── pdfco-merge/                       # Reader-facing documentation
    ├── README.md                      # Doc index and reading order
    ├── merge-pdfs.md                  # Tutorial
    ├── merge-reference.md             # Reference
    ├── credits.md                     # Explanation
    └── troubleshooting.md             # Troubleshooting
```

### Why three areas: `pdfco-merge/`, `process/`, and `process/ai/`

| Area | Audience | Purpose |
|---|---|---|
| `pdfco-merge/` | External: users | Learn how to use the merge endpoint |
| `process/` | Internal: reviewers and maintainers | Scope, lifecycle, updates, and workflow |
| `process/ai/` | Internal: authors using AI assistance | Skills and style rules for drafting |


## Navigation logic

This sample uses **README-based navigation** rather than a static site sidebar.

1. **[assignment/README.md](../README.md):** Submission index, topic selection, and component map.
2. **[pdfco-merge/README.md](../pdfco-merge/README.md):** Reader hub with page types, descriptions, and recommended reading order.
3. **Cross-links within pages:** Relative Markdown links connect related content (for example, tutorial → reference → troubleshooting).

This works for a four-page sample browsed on GitHub. At scale (roughly 50+ pages), navigation would move to autogenerated sidebars via Mintlify, MkDocs, Starlight, or Docusaurus. Plain Markdown in Git keeps the content portable across those tools.

### Reading order

Pages follow the integration journey described in the [assignment README](../README.md#what-the-reader-can-do-after-reading):

```
merge-pdfs → merge-reference → credits → troubleshooting
 tutorial      reference       explanation   troubleshooting
```

The reference sits after the tutorial because readers look up fields while building, not before they send a first test request. Credits and troubleshooting come after core integration. Readers reach them when planning usage or when something fails.

## Page types (Diátaxis framework)

This sample follows [Diátaxis](https://diataxis.fr/) for tutorial, reference, and explanation pages. Troubleshooting is treated as its own page type here.

Troubleshooting shares some traits with how-to guides. Both can include numbered steps and checklists. The reader need is different. A how-to helps someone complete a task under normal conditions. Troubleshooting helps someone diagnose and fix a failure. That focus on errors, symptoms, and remediation keeps it separate from how-to in this set, even when the page includes procedural steps.


| Diátaxis type | Reader need | Page | Why this type |
|---|---|---|---|
| **Tutorial** | "I need a first success" | [merge-pdfs.md](../pdfco-merge/merge-pdfs.md) | Learning-oriented walkthrough with cURL, sync response, and async introduction |
| **Reference** | "I need to look something up" | [merge-reference.md](../pdfco-merge/merge-reference.md) | Scannable attribute tables, response fields, profiles, and limits |
| **Explanation** | "I need to understand why" | [credits.md](../pdfco-merge/credits.md) | How credit fields work and how to plan usage without repeating field tables |
| **Troubleshooting** | "Something is broken" | [troubleshooting.md](../pdfco-merge/troubleshooting.md) | Symptom → cause → fix under failure. Procedural, but not a how-to task guide |


### What is intentionally out of scope

| Topic | Where it lives instead | Reason |
|---|---|---|
| `POST /v1/pdf/merge2` (multi-format merge) | [Official PDF.co reference](https://developer.pdf.co/api/merge/pdf) | Separate endpoint. Not part of this sample's scope. |
| Full optional attributes usage documentation | Official reference + API Tester | Profiles, encryption and other features are advanced. Reference lists these attributes, but the tutorial excludes them. |


## Scale path

